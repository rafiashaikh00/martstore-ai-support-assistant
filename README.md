Overview
martStore AI Support Assistant is a single-agent customer-support application built with Python, LangChain, LangGraph, and Streamlit. Instead of sending every message through the same response path, its workflow routes a customer request to the relevant capability: general conversation, policy question answering, order lookup, or support-ticket preparation.

The project combines language-model reasoning with retrieval, database tools, persistent conversation state, and a human approval step. It is a single-agent application with multiple workflow paths, not a multi-agent system.
Problem Statement
Online stores repeatedly receive questions such as “What is your return policy?”, “Where is my order?”, and “How can I report a damaged item?” Small support teams may not be able to respond immediately to every request. Generic chatbots can also provide inaccurate answers when they do not have access to the store’s actual policies or order records.

The project addresses the need for faster first-line support while keeping policy answers grounded in documents, order details connected to stored data, and ticket creation under human control.
Proposed Solution
The assistant classifies each customer message and routes it to an appropriate workflow:
Customer request	Workflow	Result
General conversation	General chat	A conversational answer generated by the language model
Return, shipping, or refund policy	Policy RAG	An answer grounded in retrieved policy text, with source filenames
An order ID or order-status question	Order lookup tool	Order details retrieved from the SQLite database instead of guessed
Complaint or product problem	Human-in-the-loop ticket workflow	A proposed support ticket is shown for approval or rejection before it is saved


The goal is to reduce repetitive support work without giving the assistant permission to perform sensitive order actions on its own.
Who It Is For
- Customers: people who need quick answers about store policies or their order status.
- Small online-store teams: teams that want to automate routine questions while retaining human oversight for complaints and ticket creation.
Key Features
- Intent-based routing: directs requests to general chat, policy RAG, order lookup, or ticket handling.
- Policy question answering with RAG: retrieves relevant sections from .txt policy documents and returns source filenames.
- Order lookup with tool calling: uses a tool to fetch order details from SQLite.
- Human-in-the-loop ticketing: pauses the workflow so a person can approve or reject a proposed ticket.
- Conversation history: provides a chat interface with multiple conversations.
- Persistent graph state: uses SQLite-backed LangGraph checkpoints to support restoring conversations and pending workflow state.
- Streaming responses: displays assistant responses progressively where implemented in the application.
- Bounded actions: the assistant is designed for lookup and ticket preparation; it does not independently cancel, change, or refund orders.

AI Methodology
1. Intent routing
The backend uses routing logic to choose an appropriate workflow for a customer message. Straightforward patterns can be handled with Python checks, while the language model can classify less obvious messages into the supported intent categories. This separates the application’s workflows instead of treating every request as a generic chat question.
2. Retrieval-Augmented Generation (RAG)
The RAG pipeline in data_rag.py loads policy text files from polices/, splits the text into overlapping chunks, creates embeddings, and stores them in ChromaDB. When a policy question arrives, the retriever searches for relevant chunks and passes the retrieved context to the language model. The answer can include the source filenames so the user can see which policy files informed it.

The intended benefit is to ground policy answers in the project’s documents rather than relying only on the model’s general knowledge.
3. Order lookup through tool calling
For order-related requests, the workflow can call an order-lookup tool that reads the stored order data from SQLite. The model then uses the returned database result to formulate a response. This is preferable to asking the language model to invent order status or item details.
4. Human-in-the-loop ticket handling
When a customer reports a problem, the workflow prepares a ticket summary and pauses for a human decision. The person reviewing the request can approve or reject it in the interface. The purpose of this step is to keep ticket creation under human oversight rather than silently taking the action automatically.
5. Conversation state and persistence
The application uses LangGraph state and SQLite-backed checkpointing to preserve conversation state by thread. This supports separate conversations and restoring saved state when the application is used again, subject to the configured persistence workflow.

Setup and Installation
Prerequisites
- Python 3.11 or 3.12 (use the version compatible with your installed dependencies).
- Git.
- A Groq API key from the Groq Console.
1. Clone the repository
Replace the URL with your actual public GitHub repository URL:
git clone YOUR_GITHUB_REPOSITORY_URL
cd YOUR_REPOSITORY_FOLDER
2. Create a virtual environment
Windows PowerShell:
python -m venv .venv
.venv\Scripts\Activate.ps1
If PowerShell blocks activation, you can use Command Prompt instead:
.venv\Scripts\activate.bat
macOS / Linux:
python3 -m venv .venv
source .venv/bin/activate
3. Install dependencies
pip install -r requirements.txt
4. Configure the API key
Create a .env file in the project root. If .env.example is included, copy it and replace the placeholder with your own key. For example:
GROQ_API_KEY=your_groq_api_key_here
Do not share or commit your real API key. If your backend reads the key from environment variables, make sure it is available before starting the application.
Run the Application
From the project root, with the virtual environment active, run:
streamlit run data_fron.py
Streamlit should open the application in your browser and display a local URL in the terminal. Follow any first-run setup or indexing messages shown by the app.

Current Scope and Limitations
- This is a working prototype, not a complete production customer-support platform.
- Order lookup depends on the demo SQLite data available to the application.
- The assistant does not independently cancel, modify, or refund orders.
- Ticket creation is designed to require a human approval decision.
- Policy-answer quality depends on the contents and retrieval of the policy text files.
- A public live deployment and demo video should only be listed in the submission once they have been created and tested.
